# Release Notes Updater — Between the Rolls

Цель: вести `RELEASE_NOTES.md` в корне проекта так, чтобы игрок (или будущий автор) понял, **что нового**, без чтения git history.

## Когда срабатывать

- **Явная просьба:** «обнови релиз нотс», «запиши в changelog», «добавь в RELEASE_NOTES»
- **Подготовка к новой версии:** перед bump'ом версии или релизом
- **После завершения фичи:** когда крупная задача из роадмапа закрыта
- **После серии user-facing изменений:** UI, gameplay, новые экраны, баги

**НЕ срабатывать на:**
- Чисто технический рефакторинг без изменения поведения
- Бамп зависимостей без эффекта на игрока
- Изменения в `/docs` или `/scripts`
- Опечатки в комментариях
- Изменения, которые игрок никак не заметит

Если сомневаешься — спроси пользователя, попадает ли изменение в release notes.

## Формат файла

Файл `RELEASE_NOTES.md` в корне. Структура:

```markdown
# Release Notes

## Version X.Y.Z

### Новые функции
- **Название фичи**
  - Деталь 1
  - Деталь 2

### Улучшения UI
- **Название улучшения**
  - Что именно поменялось

### Исправления
- ...

### Технические улучшения
- Краткое описание (без воды)

## Version X.Y.(Z-1)
...
```

**Текущая версия:** последняя в файле (вверху). Новые секции добавляются **сверху**, старые версии остаются ниже.

## Категории

Используй эти заголовки (в этом порядке внутри версии):

1. **Новые функции** — фича, которой раньше не было (новый экран, новый режим игры, новая возможность)
2. **Улучшения UI** — изменения в существующих экранах, layout, читаемости
3. **Исправления** — баги
4. **Технические улучшения** — рефакторинг, который игрок косвенно почувствует (стабильность, перформанс, новые архитектурные классы)

Если категория пустая — не пиши её совсем.

## Как формулировать

**Правила:**

- **На русском.** Это для игрока, не для разработчика.
- **С позиции игрока, а не кода.** Не «добавлен класс `LevelUpBuild`», а «теперь поднятие уровня показывает итоговый экран подтверждения».
- **Жирный заголовок фичи + bullet-список деталей** — как в существующих записях
- **Без жаргона** — не «z-order рефакторинг», а «исправлено перекрытие элементов интерфейса»
- **Не упоминай пути к файлам и имена классов** — это в git, не в release notes
- **Глаголы в прошедшем времени или существительные**: «Добавлен экран...», «Исправление перекрытий...»

## Когда увеличивать версию

Использует semver-подобную схему: `MAJOR.MINOR.PATCH`.

| Изменение | Версия |
|---|---|
| Крупная фича / новый режим игры (combat, автогенерация мира) | **MINOR** (0.X.0 → 0.X+1.0) |
| Несколько средних улучшений / UI-обновления | **MINOR** или **PATCH** |
| Только багфиксы | **PATCH** (0.X.Y → 0.X.Y+1) |
| Сломали обратную совместимость сейвов | обсуждается отдельно |

Для текущего pet-project'а правила гибкие. Пользователь может сам сказать, какая версия.

## Алгоритм работы

1. **Уточни область:**
   - Спроси (если непонятно): это новая версия или дописка к текущей?
   - Если новая версия — какой номер?

2. **Собери, что добавлять:**
   - Что недавно изменилось? (`git log` с момента последнего тега / последней записи в RELEASE_NOTES)
   - Что говорит пользователь?
   - Какие коммиты помечены как user-facing?

3. **Прочитай существующий `RELEASE_NOTES.md`** — для тона и формата.

4. **Сгруппируй изменения** по 4 категориям выше. Опусти пустые.

5. **Напиши** — в стиле существующих записей:
   - Жирный заголовок фичи
   - Маркированный список деталей
   - Без воды, по делу

6. **Добавь сверху, под `# Release Notes`** — старые версии не трогай.

7. **Покажи диф пользователю** до сохранения, если изменение крупное.

## Что НЕ делать

- ❌ Не дублируй то, что уже есть в предыдущих версиях
- ❌ Не пиши имена классов, файлов, путей в коде
- ❌ Не пиши номера PR/коммитов
- ❌ Не пиши даты — версия и порядок достаточно
- ❌ Не используй emoji (текущий файл их не использует)
- ❌ Не переписывай старые версии — они зафиксированы
- ❌ Не дублируй содержимое в `docs/` — release notes это **хроника**, не справочник
- ❌ Не делай записи на английском — RU primary

## Хороший vs плохой пример

❌ **Плохо:**
```
- Refactored LevelUpScreen to use LevelUpBuild class
- Added subfeatures support in `level_up_builder.py`
- Z-order issues fixed in modals (commit 4f2a1)
```

✅ **Хорошо:**
```
### Новые функции

- **Система поднятия уровня персонажа**
  - Добавлен экран поднятия уровня с пошаговым выбором новых возможностей
  - Выбор подособенностей при наличии вариантов
  - Экран подтверждения с итоговой информацией о выборе

### Улучшения UI

- **Исправление перекрытия элементов интерфейса**
  - Стандартизирован порядок отрисовки во всех экранах
  - Модальные окна рисуются после всех элементов с затемняющим overlay
```

## Чеклист перед сохранением

- [ ] Версия указана корректно (новая сверху, старые ниже)
- [ ] Категории в правильном порядке
- [ ] Только user-facing изменения (никаких рефакторингов без эффекта)
- [ ] Нет имён классов, путей, номеров коммитов
- [ ] На русском, в стиле предыдущих версий
- [ ] Старые версии не тронуты
