# Documentation Updater — Between the Rolls

Цель: поддерживать `/docs` **живой и актуальной** после изменений в коде. Документация должна отражать намерения и текущее состояние, не превращаясь в кладбище устаревшего.

## Когда срабатывать

Срабатывай **после** изменений, которые:

- Добавляют/удаляют **экран** (`game/ui/screens/`)
- Добавляют/удаляют **gameplay-режим** (`game/core/gameplay/`)
- Добавляют/удаляют **инструмент для ЛЛМ** (`game/core/tools/`)
- Меняют **системный промпт** или схему вывода (`game/core/prompts/`, `schemas/`)
- Добавляют/меняют **класс сущности** (`game/core/entities/`)
- Меняют **дефолтную модель** или провайдера ЛЛМ
- Меняют **формат сейвов**
- Удаляют **легаси** (например, `app/`, LangChain)
- Принимают **архитектурное решение** (новый ADR)
- Закрывают пункт из `production/backlog.md` или `roadmap.md`

Также срабатывай по явной просьбе: «обнови доку», «синхронизируй с кодом», «запиши решение в ADR».

## Карта «код → документ»

Какой документ обновлять при каких изменениях:

| Изменение в коде | Документ для обновления |
|---|---|
| Новый/удалённый экран | [design/ux/screens-flow.md](docs/design/ux/screens-flow.md), [tech/architecture.md](docs/tech/architecture.md) §«Слои» |
| Новый/удалённый gameplay-режим | новый файл в `design/systems/`, обновить `design/overview.md` |
| Новый инструмент ЛЛМ (`tools/`) | [tech/llm-integration.md](docs/tech/llm-integration.md) §«Инструменты» |
| Изменение системного промпта | [tech/llm-integration.md](docs/tech/llm-integration.md) + соответствующий `design/systems/<режим>.md` |
| Новый/изменённый класс entity | [tech/data-models.md](docs/tech/data-models.md) |
| Смена дефолтной LLM-модели | [tech/llm-integration.md](docs/tech/llm-integration.md), [README.md](README.md) |
| Смена LLM-провайдера | [tech/llm-integration.md](docs/tech/llm-integration.md), `README.md`, возможен новый ADR |
| Смена формата сейвов | [tech/data-models.md](docs/tech/data-models.md), [tech/adr/0002-pickle-saves.md](docs/tech/adr/0002-pickle-saves.md) (или новый ADR-superseding) |
| Удаление легаси | вычистить упоминания во всех файлах + отметить в `production/backlog.md` |
| Новое архитектурное решение | новый ADR в `docs/tech/adr/NNNN-<тема>.md` |
| Закрытие пункта роадмапа | `production/roadmap.md` (отметка `[x]`), `production/backlog.md` (перенос в «Закрытые») |

## Алгоритм работы

1. **Определи категорию изменения** (см. таблицу выше).

2. **Найди затронутые документы:**
   - Прямые — из таблицы
   - Косвенные — поиск ссылок на затронутые сущности (`Grep` по `/docs` для имён классов / файлов / понятий)

3. **Прочитай затронутые документы** перед редактированием — поймёшь текущий тон и структуру.

4. **Обнови минимально и точечно:**
   - Не переписывай разделы, которые не затронуты
   - Сохраняй стиль и заголовки
   - Используй `Edit`, не `Write` (для существующих файлов)

5. **Проверь cross-references:**
   - Если переименовал/удалил файл — обнови все ссылки
   - Если добавил новый — добавь ссылку в `docs/README.md` и в навигационных разделах

6. **Обнови roadmap/backlog:**
   - Если изменение закрывает пункт — отметь
   - Если открывает новый техдолг — добавь в `production/backlog.md`

## Когда нужен новый ADR

Новый файл в `docs/tech/adr/`, если решение:

- **Нелокально** — затрагивает несколько модулей или меняет общий подход
- **Спорно или неочевидно** — есть альтернативы, которые мы отвергли
- **Долгоживущее** — сложно потом откатить
- **Может вызвать вопрос «почему?» через 6 месяцев**

Не нужен ADR для: переименований, мелких рефакторингов, исправлений багов.

Формат ADR:

```markdown
# ADR-NNNN: Заголовок

**Дата:** YYYY-MM-DD
**Статус:** Accepted | Superseded by ADR-XXXX | Deprecated

## Контекст
Какую проблему решали.

## Решение
Что решили.

## Альтернативы
Что рассматривали и почему отвергли.

## Последствия
Плюсы и минусы.

## Связанные
Ссылки на связанные документы.
```

После создания ADR — добавь ссылку в [docs/tech/adr/README.md](docs/tech/adr/README.md).

### Уже записанный ADR править нельзя ради «актуальности»

Запись со статусом **Accepted** — это **история решения на дату файла**. Её нельзя переписывать так, чтобы текст совпадал с новым кодом: так теряется ответ на вопрос «что мы решили тогда и при каких условиях».

Если реальность изменилась:

1. Создай **новый** ADR с **следующим номером** в `docs/tech/adr/` (после максимального существующего `NNNN`).
2. В новом ADR опиши актуальное решение, контекст и блок **«Связанные»** со ссылками на предыдущие ADR (формулировка типа: *дополняет ADR-0003*, *не отменяет ADR-0004*, и т.п.).
3. **Старый ADR не редактируй** под новое состояние. Перевод старой записи в статус «Superseded by ADR-XXXX» делается только если это **явно** принято в процессе команды; по умолчанию для этого репозитория прошлый файл остаётся как есть — новый ADR продолжает хронологию.

Итог: **новое решение → новый номер ADR**, а не правка текста старого. Следующий свободный номер — по индексу в `docs/tech/adr/README.md`.

## Стиль и тон документации

**Соблюдай при обновлении:**

- Язык — **русский**, английский только для технических терминов и идентификаторов
- Заголовки — короткие, суть-первая
- Таблицы — для сравнений и списков «фича vs состояние»
- Ссылки на код — относительные, формат markdown (`[путь](путь)`)
- **Не пиши простыни** — лучше короче и точнее
- **Не дублируй то, что есть в git/коде** — описывай намерения и решения, не текущий diff

## Что НЕ делать

- ❌ Не обновляй `RELEASE_NOTES.md` — он живёт отдельно по своим правилам
- ❌ Не пиши в доку имена коммитов или PR-ов
- ❌ Не добавляй временные пометки типа «обновил 2026-05-03 после рефакторинга X» — это в git history
- ❌ Не плоди новые файлы, если можно обновить существующий
- ❌ Не удаляй разделы «Открытые вопросы» / «Известные проблемы» только потому, что они выглядят как недоделка — это полезный контент
- ❌ Не правь текст уже принятых ADR под актуальный код — см. подраздел **«Уже записанный ADR править нельзя…»** в «Когда нужен новый ADR»; изменение фиксируй **новым** ADR со ссылками в «Связанные»

## Чеклист после изменения

После работы скилла проверь:

- [ ] Все упомянутые в коде имена классов/файлов соответствуют тому, что есть в репозитории
- [ ] Ссылки между документами не сломаны
- [ ] `docs/README.md` упоминает новые файлы (если добавил)
- [ ] `production/roadmap.md` или `backlog.md` обновлены, если изменение их касается
- [ ] Тон и формат соответствуют существующим документам
- [ ] Если затронут [README.md](README.md) в корне — он тоже обновлён

## Принципы (важно)

- **Лучше короткая актуальная страница, чем длинная устаревшая.** Если раздел стал неточным — урезай.
- **Решения важнее результатов.** *Почему* так > *что* так. ADR — главное, что мы оставляем потомкам.
- **Дока — это договор о намерениях.** Не превращай её в авто-генерируемый отчёт о коде.
