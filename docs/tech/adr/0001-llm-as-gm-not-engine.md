# ADR-0001: ЛЛМ — Мастер, а не Движок

**Дата:** 2026-05-03 (зафиксировано задним числом)  
**Статус:** Accepted

## Контекст

В ранней версии проекта ЛЛМ был **движком игры**: отвечал за броски кубиков, изменение инвентаря, расчёт боя, генерацию урона, ведение HP. Всё состояние мира хранилось внутри контекста модели (в истории сообщений).

Это привело к проблемам:

- **Галлюцинации** — модель «забывала» предметы из инвентаря, путалась в HP, противоречиво описывала состояния
- **Разрастание контекста** — каждое действие добавляло токены, стоимость росла нелинейно
- **Невоспроизводимость** — два запуска одного действия могли дать разные результаты
- **Невалидные броски** — модель могла «накатить» 25 на d20

## Решение

ЛЛМ играет **роль Мастера Подземелий**: описывает, реагирует, тактически решает, но **не модифицирует мир напрямую**.

Все изменения мира — через **инструменты (Python-функции)**, которые ЛЛМ вызывает:

- `roll_dice()` — настоящий бросок в Python
- `rule_db_lookup()` — обращение к базе правил
- (план) `create_npc()`, `create_location()`, `apply_damage()`, `add_item_to_inventory()`, и т.д.

Состояние мира — в `MainGameState`, в Python-объектах. ЛЛМ получает релевантную часть в системном промпте.

## Альтернативы

1. **Полностью движковый подход (без ЛЛМ)** — скриптованная RPG. Отвергнут, потому что главный USP проекта — свобода действий и автогенерация.
2. **ЛЛМ-как-движок (старый подход)** — отвергнут из-за галлюцинаций.
3. **Гибрид с проверкой ЛЛМ-вывода** — отвергнут как избыточно сложный (всё равно нужны Python-функции).

## Последствия

**Плюсы:**
- Воспроизводимые броски (можно seedить random)
- Состояние не теряется
- Можно сохранять и грузить
- Дешевле в токенах
- Можно добавить детерминистичные тесты gameplay-механик

**Минусы:**
- Каждая новая механика требует **двух работ**: Python-функции + промпт-инструкции, чтобы ЛЛМ её использовал
- ЛЛМ может «забыть» вызвать инструмент — нужны явные инструкции в промпте
- Расширение мира требует расширения tooling (`create_npc` и т.д.)
